## 二、建设目标

运行时同时支持三种明确的 Skill 输入方式，并保持现有 Repository 调用兼容：

1. 直接读取本地或市场提供的 `SKILL.md`。
2. 接收业务系统从数据库查询并组装好的 Python 对象。
3. 保留当前通过 `SkillRepository` 和 `ToolRepository` 按 Skill ID 编译的入口。

三种入口必须转换成同一个内部 `SkillDocument`，随后共用 Tool 校验、Adapter 构建、Prompt 编译、执行保护和指纹生成逻辑。核心库不依赖数据库、ORM、Web 框架或具体存储实现。

## 三、非建设范围

- 不在核心库中连接数据库或定义业务表结构。
- 不根据字符串内容自动猜测它是文件路径还是 Skill ID。
- 不在 `SKILL.md` 中执行内嵌 Python、Shell 或 JavaScript 源码。
- 不改变 Function Registry、Script Executor、Client Transport、MCP Client 和 SecretProvider 的职责边界。
- 不把测试代码、测试 Skill 或测试 MCP Server 打入 wheel。

## 四、总体架构

```text
SKILL.md ───────────────> compile_file() ─────┐
                                              │
Skill + Tool 对象 ──────> compile_objects() ──┼──> SkillDocument
                                              │          ↓
Repository + Skill ID ──> compile() ──────────┘   _compile_document()
                                                         ↓
                                              PromptCompiler + ToolFactory
                                                         ↓
                                                    SkillBundle
```

### 4.1 核心原则

- 输入来源只负责加载和规范化数据。
- `SkillDocument` 是唯一内部编译输入。
- `ToolFactory` 和四种 ToolAdapter 不感知输入来自文件、对象还是 Repository。
- 每次调用只使用一种输入来源，不进行来源覆盖或合并。
- 文件模式和对象模式不要求配置 Repository。

## 五、公共 API

### 5.1 文件模式

```python
bundle = await runtime.compile_file(
    "/path/to/skill/SKILL.md",
    context=compile_context,
)
```

行为：

1. 读取 UTF-8 编码的 `SKILL.md`。
2. 解析 YAML Frontmatter 和 Markdown 正文。
3. 将 Frontmatter 中的 `tools` 转换为 Tool 定义。
4. 将相对脚本入口限定并解析到 `SKILL.md` 所在目录内。
5. 编译并返回 `SkillBundle`。

`tools` 可以省略。没有 `tools` 的市场 Skill 被视为纯 Prompt Skill，仍然可以得到只包含系统提示词的 `SkillBundle`。

### 5.2 对象模式

```python
bundle = await runtime.compile_objects(
    skill=skill_definition,
    tools=resolved_tool_definitions,
    context=compile_context,
)
```

业务系统可以从数据库、配置中心或任意存储中读取数据，但必须在调用核心库前转换成 `SkillDefinition` 和 `ResolvedToolDefinition`。核心库不关心对象如何持久化。

### 5.3 Repository 兼容模式

```python
bundle = await runtime.compile(
    "skill-id",
    compile_context,
)
```

该入口保持现有行为：

1. 从 `SkillRepository` 读取 `SkillDefinition`。
2. 从 `ToolRepository` 读取已经合并关系和权限的 `ResolvedToolDefinition`。
3. 委派给 `compile_objects()`。

如果运行时没有配置 Repository，却调用了 `compile()`，必须抛出固定、安全的运行时配置错误。

### 5.4 运行时构造

`tool_factory` 是所有模式的必需依赖，Repository 改为可选依赖：

```python
runtime = SkillRuntime(tool_factory=tool_factory)
```

旧项目继续使用：

```python
runtime = SkillRuntime(
    skill_repository=skill_repository,
    tool_repository=tool_repository,
    tool_factory=tool_factory,
)
```

## 六、统一中间模型

新增只在核心编译层使用的不可变对象：

```python
class SkillDocument(BaseModel):
    id: str
    name: str
    description: str
    version: str
    instructions: str
    tools: tuple[ResolvedToolDefinition, ...]
    source_root: Path | None = None
    metadata: dict[str, Any] = Field(default_factory=dict)
```

字段含义：

- `id`：Skill 稳定标识；文件模式默认使用 Frontmatter 的 `id`，缺省时使用 `name`。
- `name`、`description`：Skill 对外名称和描述。
- `version`：文件模式缺省为 `0.0.0`，对象模式使用对象版本。
- `instructions`：未经改写的 Markdown 正文。
- `tools`：已完成来源规范化的 Tool 定义。
- `source_root`：文件模式下为 `SKILL.md` 父目录，对象模式为 `None`。
- `metadata`：非执行型扩展信息，不自动注入 Prompt。

## 七、SKILL.md Frontmatter 规范

基础字段：

```yaml
---
name: heterogeneous-tools
description: 异构工具测试技能
version: 1.0.0
tools: []
---
```

兼容规则：

- `name` 和 `description` 必填。
- `id`、`version`、`compatibility`、`metadata` 和 `tools` 可选。
- 继续解析市场 Skill 中的 `allowed-tools`，但它只作为兼容信息和诊断依据，不能凭名称创建可执行 Tool。
- `tools` 是文件模式下可执行 Tool 的唯一来源。
- `tools` 缺省或为空时，编译纯 Prompt Skill。
- Tool 的 `id` 缺省为 Tool 名称，`version` 缺省为 Skill 版本。
- Tool 的 `required` 和 `enabled` 默认是 `true`，`sort_order` 默认使用其在 `tools` 列表中的顺序。
- Tool 的 `timeout_seconds` 默认是 30 秒，`max_output_bytes` 默认是 1 MiB。
- Frontmatter 的 `execution` 在规范化时映射为内部 `execution_config`。

### 7.1 Python Function

```yaml
tools:
  - name: add_numbers
    description: 计算两个数字之和
    type: PYTHON_FUNCTION
    version: 1.0.0
    input_schema:
      type: object
      properties:
        a: {type: integer}
        b: {type: integer}
      required: [a, b]
      additionalProperties: false
    output_schema:
      type: integer
    execution:
      registry_key: math.add
```

### 7.2 服务端脚本

```yaml
tools:
  - name: generate_report
    description: 生成报告
    type: SERVER_SCRIPT
    input_schema:
      type: object
      properties:
        title: {type: string}
      required: [title]
    execution:
      entry: scripts/generate_report.py
```

文件模式会验证 `entry` 是相对路径，且规范化后的路径仍位于 Skill 根目录内。通过验证后，将其转换为 Script Executor 可接收的 `artifact_id`。对象模式继续直接使用业务系统提供的 `artifact_id`。

### 7.3 客户端 JavaScript

```yaml
tools:
  - name: export_file
    description: 委派客户端导出文件
    type: CLIENT_JAVASCRIPT
    input_schema:
      type: object
      properties:
        format: {type: string}
      required: [format]
    execution:
      tool_key: client.export.file
```

### 7.4 MCP

```yaml
tools:
  - name: query_hotel
    description: 调用酒店 MCP 工具
    type: MCP
    input_schema:
      type: object
      properties:
        hotel_id: {type: string}
      required: [hotel_id]
    execution:
      server_name: hotel-mcp
      tool_name: query_hotel
      server_ref: mcp/hotel
```

文件模式不接受内联 `server`，避免第三方 Skill 通过 stdio `command` 启动本地进程，或在 URL、Header、环境变量中携带明文凭据。`server_ref` 必须由宿主注入的 `McpServerConfigProvider` 解析成经过审核的连接配置；配置中的密钥继续使用 `secret_ref` 并由 `SecretProvider` 解析。对象模式属于业务系统已完成治理的数据，兼容直接提供 `server`，同时也可以使用 `server_ref`。

## 八、数据流

### 8.1 文件模式

```text
文件路径
  -> SkillFileLoader
  -> SkillParser
  -> Frontmatter Tool 规范化
  -> SkillDocument
  -> _compile_document()
  -> SkillBundle
```

### 8.2 对象模式

```text
SkillDefinition + ResolvedToolDefinition[]
  -> Skill Markdown 解析
  -> SkillDocument
  -> _compile_document()
  -> SkillBundle
```

### 8.3 Repository 模式

```text
skill_id + CompileContext
  -> SkillRepository + ToolRepository
  -> compile_objects()
  -> SkillDocument
  -> _compile_document()
  -> SkillBundle
```

## 九、校验与错误

- 文件不存在：`SkillFileNotFoundError`。
- 文件无法按 UTF-8 读取：`SkillReadError`。
- Frontmatter 或 Markdown 非法：`SkillParseError`。
- 运行时缺少 Repository：`SkillRuntimeConfigurationError`。
- Tool 类型、Schema 或执行配置非法：`ToolDefinitionError`。
- 必需 Tool 构建失败：`SkillCompileError`。
- 可选 Tool 构建失败：跳过并写入 diagnostics。
- Tool 执行超时、输出校验、输出大小和安全异常净化继续使用当前统一调用守卫。

所有公开错误不得包含 Secret、原始执行异常、内部绝对路径或敏感参数全文。

## 十、安全约束

- 不执行 YAML 中的内嵌源码。
- Function 只允许引用 Function Registry 中已注册的 `registry_key`。
- 脚本 `entry` 不允许绝对路径或通过 `..` 逃逸 Skill 根目录。
- 客户端只允许调用预注册的 `tool_key`。
- 文件型 MCP 只允许引用宿主预注册的 `server_ref`，不允许 Frontmatter 提供原始连接或进程配置。
- 宿主 MCP 配置中的密钥只允许使用 `secret_ref`。
- Tool 名称必须唯一并符合模型调用名称约束。
- JSON Schema 使用 Draft 2020-12 校验。

1. 真实 `SKILL.md` 同时声明 Function、服务端脚本、客户端和 MCP 四类 Tool。
2. `compile_file()` 编译并执行四类 Tool。
3. `compile_objects()` 使用等价对象编译并执行四类 Tool。
4. 两种模式得到相同的工具名称、Prompt、诊断规则和执行结果。
5. 旧 `compile(skill_id, context)` 测试继续通过。
6. 纯 Prompt 市场 Skill 在没有 `tools` 时正常编译。
7. 文件不存在、非法 YAML、非法 Tool Schema、脚本路径逃逸均有失败测试。
8. 文件型 MCP 的内联 stdio 命令、环境变量和明文 Header 均被拒绝。
